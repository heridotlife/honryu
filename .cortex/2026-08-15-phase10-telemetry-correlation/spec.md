# Phase 10 — Telemetry correlation

Agreed via brainstorm 2026-08-15, continuing the brainstorm → write-plan →
execute-plan cadence of Phases 5–9. This is (B) from Phase 9's hand-off note
(`.cortex/2026-08-12-phase9-analytics-telemetry/spec.md`): the telemetry-
correlation half of the roadmap's Phase 9 one-liner that Phase 9 deliberately
scoped out, and resolved decision #10 in the parent spec
(`.cortex/2026-07-30-honryu/spec.md`): "Engines send W3C `traceparent` plus
Honryu correlation headers (run, execution, service, tenant); reports surface
those identifiers and the run's time window so users jump into their own APM.
Honryu emits no spans of its own and does not own a trace pipeline."

## Problem

A run's report tells a reader *that* a service failed or was slow, but not
*why* — the target's own APM has the internals (server-side spans, DB query
times, downstream calls), and today there is nothing joining a Honryu run to
that data. A reader has to manually reconstruct "what was Honryu doing at
14:32:07" from a report's time window and go hunting in the APM by hand.

## Goal

Every request Honryu's generated load sends carries a stable, run-scoped
identity a customer's APM can filter or tag on, and the report surfaces that
same identity — so "this run looked bad, go look at the target's traces for
it" is a copy-paste, not a reconstruction.

## Non-goals

- **No spans of Honryu's own, no trace pipeline.** Propagate-and-hope-it-helps,
  not build-an-APM. Carried forward unchanged from resolved decision #10.
- **No per-request unique trace IDs.** Taurus `headers:` are static YAML
  strings; generating a fresh id per HTTP request needs per-engine scripting
  (a JMeter function, k6 JS, ...) — exactly the per-engine coupling this
  rebuild deleted. One static `traceparent`/`baggage` pair covers the whole
  run, applied via `headers:`, not per request.
- **No rewriting or post-processing a native script beyond Taurus's own
  `headers:` scenario option.** No custom JMX `HeaderManager` injection, no k6
  script rewriting. Honryu delegates to bzt's own config-override mechanism,
  matching "delegate execution to Taurus; do not reinvent bzt." If a given
  native engine's executor does not honor scenario-level `headers:`, that
  engine's requests simply do not carry them — a documented per-engine
  limitation, not a Honryu-side workaround to build in v1.
- **No customer-configurable sampling.** The `traceparent` sampled flag is
  always off (`00`) in v1. Revisit only if a customer asks.
- **No UI.** API-first, consistent with Phases 7–9; the correlation id is a
  new field on the existing report response.
- **No new external dependency.** `crypto/rand` (stdlib) is sufficient; no
  OTel SDK.

## Constraints

### Technical / structural

- **A run id does not exist at compile time.** `compileShards` runs inside
  `lifecycleapp.Service.Deploy` (`service.go:568`); `StartRun` — which mints
  the run id — only happens later, inside `Trigger` (`service.go:387`), by
  which point `Deploy`'s pods may already be executing `bzt` (the engine
  script execs it the moment the pod starts, confirmed by task 23c's fix).
  So the correlation id **cannot** be the DB run id threaded backwards into
  the config; it has to be minted at `Deploy` time and threaded *forwards*.
- **One `Deploy` call corresponds to one real run in practice.** Confirmed
  from actual callers: `cmd/scheduler/main.go:180-184` calls `Deploy` then
  `Trigger` back-to-back for every scheduled firing, and a pod's `bzt` never
  reruns on its own once started (task 23c's exit-code-then-`sleep infinity`
  fix) — a second `Trigger` without a redeploy finds nothing left to run. So a
  fresh id minted once per `Deploy` and threaded forward is, in practice, a
  genuinely per-run id, not merely per-execution.
- **`compile` package stays pure.** No randomness, no I/O
  (`internal/domain/compile/compile.go`'s own package doc). The random
  trace/parent id is generated by the caller (`lifecycleapp`, which already
  does I/O) and handed in as a plain value, the same pattern `ScriptPath` and
  `DefaultAddress` already use.
- **`taurus.Scenario.Headers` already exists and is currently unused** —
  `compileScenario` never sets it today. This is the injection point; no new
  domain field on `taurus.Scenario` is needed.
- **Hexagonal, matching Phases 5–9.** Header formatting from identifiers is a
  pure, table-tested function; only random-id *generation* is I/O and lives in
  `lifecycleapp`.

### Wire format

- **`traceparent`** (W3C, `version-trace_id-parent_id-flags`): a fresh,
  random 16-byte trace id and 8-byte parent id, generated once per `Deploy`
  call via `crypto/rand`, hex-encoded — not derived from padding the numeric
  tenant/execution/project ids (avoids ever encoding internal ids, however
  faintly, into a third-party system; W3C's own spec recommends random
  generation anyway). Sampled flag always `00`.
- **`baggage`** (W3C): `honryu.tenant=<id>,honryu.service=<project id>,honryu.execution=<id>,honryu.run=<trace id>` —
  the actually-queryable identity. Reuses `baggage` rather than inventing a
  bespoke header: several OTel-based APM SDKs already promote `baggage`
  entries to span attributes without extra customer-side config, and this
  project already prefers community vocabulary over invented terms (the same
  reasoning that made Taurus the execution contract).
- The run's correlation id **is** the `traceparent` trace id — one generated
  value, not two separate identifiers to keep in sync.
- Both headers are identical across every scenario and every shard compiled
  within one `Deploy` call (including a `CalibrateEngine` deploy — calibration
  fires at a real target too, so it is not special-cased out).

### Safety / correctness

- Injected headers must not silently clobber a user's own scenario/request
  headers in a way that is surprising: since `taurus.Scenario.Headers` is
  currently unused, there is no existing scenario-level collision. A
  per-request header the user declares with the same key (`traceparent` /
  `baggage`) wins over Honryu's scenario-level default under bzt's normal
  per-request-overrides-scenario-default merge — accepted as an extremely
  unlikely, self-inflicted edge case, not solved with extra merge logic.
- Backward compatible: a run from before this phase has no stored correlation
  id; its report shows one absent/empty, never an error.

### Verification bar (as Phases 5–9)

`go build` / `vet` / `gofmt` / `golangci-lint`, unit tests, MySQL conformance
for the widened run-repository methods, e2e. **Live verification is a gate,
not optional, for the one genuinely unverified claim in this phase:** whether
`taurus.Scenario.Headers` actually reaches requests for a **native** (JMX or
other script-based) scenario, not just a portable/declarative one — this is
bzt/Taurus executor behavior Honryu's own code cannot confirm by inspection.
Verify against real bzt for at least a JMeter-native scenario and a
portable/declarative scenario; document any engine found not to honor it as a
stated limitation rather than silently claiming universal coverage.

## Approach

### Minting and threading the id

1. `lifecycleapp.Service.Deploy` generates one `TraceContext` (random 16-byte
   trace id + 8-byte parent id) at the top of the call, before its
   per-scenario loop — one value for the whole deploy.
2. A pure function (new small domain package, e.g. `internal/domain/telemetry`)
   renders `{traceparent, baggage}` from that `TraceContext` plus the
   execution's identity (`TenantID`, `ProjectID`, `ExecutionID`) already
   available in `compile.Input`'s `Execution`. Table-tested, no I/O.
3. `compile.Input` gains a `Headers map[string]string` field; `compileScenario`
   sets it on the resulting `taurus.Scenario.Headers` unconditionally.
   `compileShards` threads the same map into every shard's `compile.Input`
   within one `Deploy` call.
4. `Deploy` persists the freshly generated trace id against the execution row
   (a new narrow setter on `ExecutionRepository`, shaped like the existing
   `SetExecutionCriteria`) so it survives until the next `Trigger`.
5. `Trigger` reads it back (already loads the execution via `GetExecution`)
   and passes it into a widened `RunRepository.StartRun(ctx, executionID,
   correlationID)`, which stamps it onto the new run's row
   (`RunRecord.CorrelationID`).
6. Report finalization (already reads run identity to build `report.Meta`)
   copies the run's stored correlation id onto `Report.CorrelationID` /
   `Meta.CorrelationID` — the same shape `Cluster` was threaded through in
   Phase 8 (`execution` → `deploy`/`trigger` → `report`).

### Surfacing

- `Report.CorrelationID` is a headline field on the existing report response
  (no new endpoint) — a reader sees it beside the run's `StartedAt`/`EndedAt`
  window, satisfying resolved decision #10's "identifiers and the run's time
  window" directly.
- The exact literal `traceparent`/`baggage` strings that were sent remain
  inspectable via the existing per-shard config endpoint
  (`GET /api/runs/{run_id}/scenarios/{scenario_id}/shards/{shard}/config`,
  `openapi.yaml:1600`) — no new debug surface needed.

### Rejected alternatives

- **Deterministic id derived from stable identifiers (tenant + execution +
  scenario + cluster), recomputed on demand, no new persistence.** Cheaper,
  but every run of a recurring execution (Phase 5 scheduling) would share one
  id forever — an APM deep link would return every historical run's traffic
  mixed together, disambiguated only by the reader manually applying the
  report's time window. Rejected in brainstorm: the fresh-per-deploy id is
  only a modest amount more plumbing (well precedented by Phase 8's `Cluster`
  threading) for a materially better result — a deep link that shows exactly
  one run, full stop.
- **A bespoke `X-Honryu-*` correlation header instead of W3C `baggage`.**
  Rejected: `baggage` is the standard sibling of `traceparent` for exactly
  this purpose, costs nothing extra to build, and several APM SDKs already
  understand it.
- **`traceparent` sampled flag on by default.** Rejected: forces a compliant
  target SDK to export every one of a run's requests as spans under one
  reused trace id, which both distorts the very load being measured (added
  tracing overhead on the target) and produces an unrenderable trace in most
  APM UIs (a trace is modeled as one causal chain, not tens of thousands of
  independent requests).

## Acceptance criteria

1. Every compiled scenario in a deploy carries a valid W3C `traceparent`
   (`00-<32 hex>-<16 hex>-00`) and `baggage`
   (`honryu.tenant=…,honryu.service=…,honryu.execution=…,honryu.run=…`) header,
   applied scenario-wide via `taurus.Scenario.Headers`, with zero per-engine
   code.
2. The trace id is generated fresh and randomly once per `Deploy` call — never
   derived from stable identifiers — and is byte-identical across every
   scenario and shard belonging to that one deploy.
3. The sampled flag is always `00`; no override path exists in v1.
4. The id set at `Deploy` survives to the run it precedes: `StartRun` persists
   it, and the finalized report exposes it as `Report.CorrelationID` /
   `Meta.CorrelationID`, next to the run's existing time window.
5. A run predating this phase shows an empty/absent correlation id, never an
   error.
6. Random generation lives in `lifecycleapp`; `internal/domain/compile` gains
   no randomness or I/O. Header formatting from identifiers is pure and
   table-tested.
7. Live-verified against real bzt for at least one native (JMeter) and one
   portable/declarative scenario; any engine that does not honor
   scenario-level `headers:` for a native script is named as a documented
   limitation.
8. e2e: a triggered run's compiled config (via the existing shard-config
   endpoint) contains both headers with a well-formed trace id, and the run's
   finalized report shows the same id.
9. `go build`/`vet`/`gofmt`/`golangci-lint`, unit tests, MySQL conformance for
   the widened run-repository methods, `scripts/coverage.sh` all pass.

## Open questions

None blocking — all forks raised in brainstorm were resolved:

- ID granularity: **fresh per deploy**, not stable-per-execution (decided).
- Header shape: **W3C `traceparent` + `baggage`**, not a bespoke header
  (decided).
- Sampled flag: **always off in v1** (decided).
- Trace id encoding: **random, not padded from stable ids** (decided).

The one remaining unknown — whether native-engine executors other than
JMeter honor scenario-level `headers:` — is not a blocking design question,
it is a verification task carried into the acceptance criteria (#7) and the
execution-time verification bar.

## Live verification findings (task 121, 2026-08-16)

Live verification against `httpbin.pve.heri.life` (`/headers` echo) on the real
Talos cluster (`admin@talos-homelab`, namespace `honryu`), API image
`registry.pve.heri.life/honryu/honryu-api:phase10` built from `feat/honryu` at
`9056362`, engine image `engine-jmeter:5.6.3` unchanged. **AC7's gate is met:
the one genuinely unverified claim — that scenario-level `headers:` reaches the
wire for a *native* script — is confirmed for JMeter.** Three passing runs:

| Run | Kind | Executor | Samples | Errors | Correlation id (= config trace id) |
|-----|------|----------|---------|--------|------------------------------------|
| 2 | native (uploaded JMX) | jmeter/bzt | 50,848 | 0% | `580d8f61…7575703` |
| 3 | portable (declarative requests.yml) | jmeter/bzt (apiritif) | 47,765 | 0% | `455a605d…1f44c6f` |
| 5 | portable, second deploy | jmeter/bzt | 52,783 | 0% | `4e4eeb06…61b4f032` |

### How wire presence was proven

The target echoes request headers in the response body, and each scenario
carried its own **response assertion** requiring the substrings `traceparent`
and `honryu.run=` in that body — so a passing run means every sampled response
contained them, i.e. the headers were actually sent. A **negative control**
(the same JMX run under raw JMeter with no headers injected, reproduced in the
engine image via docker) fails with `Test failed: text expected to contain
/traceparent/`, proving the assertions bind rather than pass vacuously. bzt's
own modified-JMX artifact additionally shows the mechanism directly: scenario
headers are merged into a native script as a **plan-level `HeaderManager`**
with the exact deployed values.

### Correlation chain, live

- Each run's shard config (`GET /api/runs/{run}/…/config`) and finalized report
  carry the *same* trace id; runs 2/3/5 across three deploys minted three
  distinct ids — fresh-per-deploy confirmed live.
- After execution 3 was redeployed (overwriting its pending id), run 3's report
  still returned its original `455a605d…` — the sourced-from-history, not
  execution, decision verified against a real MySQL.
- These executions were created via the public API (no tenant), so `baggage`
  live-rendered three entries with `honryu.tenant` omitted — the nil-tenant
  branch behaving as designed; the four-entry form is covered by e2e with a
  seeded tenant (task 120).

### Engine coverage and limitations

- **JMeter: verified**, both native-script and declarative paths.
- **k6: not live-verified** — this deployment configures no k6 engine image
  (`HONRYU_ENGINE_IMAGES` lists only jmeter). Its scenario-header behavior
  remains unverified; no engine was found *not* to honor `headers:`, but k6's
  status is honestly "untested live", per the spec's naming rule.

### Incidental live findings (not phase-10 defects)

1. **JMeter assertion JMX quirk (fixture gotcha).** Assertion test strings live
   under the typo'd property `Asserion.test_strings` (a permanent JMeter
   compat typo; bzt's own writer uses it too) as bare `stringProp` items. A
   correctly-spelled `Assertion.test_strings` *loads without error but binds
   zero strings* — assertions then pass vacuously. Any future native-script
   verification fixture must use the typo'd name.
2. **`POST /trigger` has no readiness retry** (unlike `cmd/scheduler`'s
   bounded `triggerWhenReady`): fired immediately after deploy it 409s until
   the engine pod is ready (seconds); a client-side retry succeeds. Matches
   phase 7 finding #2's scope — the API path just exposes it.
3. **Deploy-then-late-trigger strands a run.** An engine pod starts generating
   load at deploy; if Trigger lands minutes later (as in one manual attempt),
   `StartRun` opens a run whose engine already sent its Final — the run sits
   "running" with no report until stopped. Reinforces that callers must
   trigger promptly after deploy, as the scheduler does.
4. **Scenario files are immutable** — re-uploading `s.jmx` to an existing
   scenario is rejected (`ports: file already exists`). A changed script needs
   a new scenario; by design, but worth knowing live.
